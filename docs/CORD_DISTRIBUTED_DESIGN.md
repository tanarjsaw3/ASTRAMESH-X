## 1. System Overview and Distributed Philosophy

The core architectural strength of Continuous Riemannian Dynamics (CORD) lies in its **block-diagonal kinetic energy formulation**:
$$\mathcal{K}(\xi) = \frac{1}{2} \sum_{i=1}^N \xi_i^\top M_i \xi_i$$
Unlike classical second-order solvers (e.g., Gauss–Newton or Levenberg–Marquardt) which require solving a large, coupled linear system $(J^\top \Omega J + \lambda I) \Delta X = -J^\top \Omega r$ at every iteration via distributed conjugate gradient or Schur complement factorizations, CORD's equations of motion are decoupled across nodes:
$$M_i \dot{\xi}_i = \operatorname{ad}_{\xi_i}^*(M_i \xi_i) - D_i \xi_i - \nabla_{X_i} \mathcal{C}(X)$$
Coupling between different poses and different robots occurs **exclusively through the potential force (Riemannian gradient $\nabla_{X_i} \mathcal{C}(X)$)**, which depends only on the 1-hop topological neighbors of node $i$ in the pose graph $\mathcal{G} = (\mathcal{V}, \mathcal{E})$.

This design translates directly into a distributed, message-passing execution model for multi-rover planetary swarms in AstroMesh-X.

## 2. Multi-Rover Model, Pose Ownership, and Boundary Variables

### 2.1 Multi-Rover Partitioning

Let $\mathcal{R} = \{1, \dots, R\}$ denote the set of autonomous rovers in the swarm.
- The global vertex set $\mathcal{V}$ is partitioned into disjoint subsets:
  $$\mathcal{V} = \bigcup_{\alpha \in \mathcal{R}} \mathcal{V}_\alpha, \qquad \mathcal{V}_\alpha \cap \mathcal{V}_\beta = \emptyset \quad (\forall \alpha \ne \beta)$$
  where $\mathcal{V}_\alpha$ contains all poses generated by Rover $\alpha$.
- In AstroMesh-X, each pose is identified by `NodeId(rover_id, index)`. Ownership is immutable: Rover $\alpha$ has exclusive write authority over configurations $X_i \in \mathrm{SE}(2)$ and velocities $\xi_i \in \mathbb{R}^3$ for all $i \in \mathcal{V}_\alpha$.

### 2.2 Boundary Nodes and Inter-Rover Coupling

Edges $\mathcal{E}$ are classified into:
1. **Local Edges ($\mathcal{E}_{\mathrm{local}} \subset \mathcal{E}$):** Edges $(i, j)$ where $i, j \in \mathcal{V}_\alpha$. Computed, stored, and evaluated entirely within Rover $\alpha$.
2. **Inter-Rover Edges ($\mathcal{E}_{\mathrm{inter}} \subset \mathcal{E}$):** Edges $(i, j)$ where $i \in \mathcal{V}_\alpha$ and $j \in \mathcal{V}_\beta$ ($\alpha \ne \beta$).
   - Node $i \in \mathcal{V}_\alpha$ is a **local boundary node** of Rover $\alpha$.
   - Node $j \in \mathcal{V}_\beta$ is a **remote boundary node** with respect to Rover $\alpha$.

To evaluate the local gradient $\nabla_{X_i} \mathcal{C}(X)$ for boundary node $i$, Rover $\alpha$ requires knowledge of the remote configuration $X_j$. Rover $\alpha$ does **not** need the internal trajectory poses of Rover $\beta$ ($\mathcal{V}_\beta \setminus \{j\}$), ensuring minimal communication overhead.

## 3. Communication Protocol and State Exchange

### 3.1 Boundary State Message Format

When an inter-rover loop closure $(i, j)$ is verified by the geometric gating pipeline (Phase 2 Milestone 2.4), Rover $\beta$ must periodically stream the state of node $j$ to Rover $\alpha$.

The canonical `BoundaryStatePacket` structure:
```cpp
struct BoundaryStatePacket {
    uint32_t sender_rover_id;   // ID of transmitting rover (beta)
    uint32_t target_rover_id;   // ID of receiving rover (alpha)
    uint64_t node_index;        // Index of the boundary node j
    uint64_t sequence_number;   // Monotonically increasing per-node packet counter
    uint64_t timestamp_ns;      // Transmitter wall/simulation timestamp in nanoseconds
    double   x;                 // Current x translation in meters
    double   y;                 // Current y translation in meters
    double   theta;             // Current heading in radians
    double   v_x;               // Current body linear velocity x in m/s
    double   v_y;               // Current body linear velocity y in m/s
    double   omega;             // Current body angular velocity in rad/s
};
```

#### Communication Bandwidth Footprint
- Header + identifiers: $4 + 4 + 8 + 8 + 8 = 32$ bytes.
- Pose state $(x, y, \theta)$: $3 \times 8 = 24$ bytes.
- Tangent velocity twist $(v_x, v_y, \omega)$: $3 \times 8 = 24$ bytes.
- Total binary packet payload: **80 bytes** per boundary node update.
- Unlike full dense Hessian transmissions in distributed Gauss–Newton (which scale as $\mathcal{O}(|\mathcal{V}_{\mathrm{boundary}}|^2)$), CORD communication scales strictly as $\mathcal{O}(|\mathcal{V}_{\mathrm{boundary}}|)$.

### 3.2 Out-of-Order and Stale Message Handling

Planetary wireless mesh networks suffer from variable packet latency, jitter, and packet reordering.
1. **Sequence Number Filtering:**
   Each rover maintains the latest received sequence number $S_j^{\max}$ for each remote boundary node $j$.
   $$\text{If } \text{packet.sequence\_number} \le S_j^{\max} \implies \text{DROP (Duplicate or Out-of-Order)}$$
   $$\text{If } \text{packet.sequence\_number} > S_j^{\max} \implies S_j^{\max} \leftarrow \text{packet.sequence\_number}, \; \text{ACCEPT}$$
2. **Age Threshold Filtering:**
   Let $t_{\mathrm{curr}}$ be the receiver's current simulation clock. If the packet transit delay exceeds maximum allowable stale threshold:
   $$\tau = t_{\mathrm{curr}} - \text{packet.timestamp\_ns} > \tau_{\mathrm{stale\_max}}$$
   the packet is flagged as stale.

## 4. Neighbor-State Prediction Under Communication Delay

### 4.1 Theoretical Principle from Shin et al. (RSS 2026)

In distributed optimization under network latency $\tau > 0$, using a delayed neighbor pose $X_j(t - \tau)$ in the gradient evaluation creates phase lag that can induce oscillatory instability or divergence in second-order dynamical systems.

Shin et al. introduced **Velocity-Extrapolated Neighbor Prediction**:
Instead of evaluating the residual with the stale pose $X_j(t - \tau)$, the receiver extrapolates the neighbor's state forward along its Riemannian geodesic using its reported body velocity $\xi_j(t - \tau)$:
$$\boxed{ \widehat{X}_j(t) = X_j(t - \tau) \exp\left( (\tau \xi_j(t - \tau))^\wedge \right) }$$

### 4.2 Application to Planar $\mathrm{SE}(2)$

In AstroMesh-X, given received pose $X_j(t - \tau) = (x_j, y_j, \theta_j)$ and twist $\xi_j = [v_{x,j}, v_{y,j}, \omega_j]^\top$:
1. The forward predicted heading is:
   $$\widehat{\theta}_j(t) = \theta_j(t - \tau) + \tau \omega_j$$
2. The forward predicted translation is:
   $$\widehat{t}_j(t) = t_j(t - \tau) + R(\theta_j) V(\tau \omega_j) (\tau v_j)$$
   where $V(\cdot)$ is the left Jacobian of $\mathrm{SO}(2)$ derived in `docs/CORD_MATHEMATICAL_FORMULATION.md`.

### 4.3 Fallback and Safety Disabling Criteria

Extrapolation along tangent velocity assumes approximately constant velocity over interval $\tau$. If network delay is excessive or velocity is high, forward extrapolation can overshoot and produce non-physical poses.

**Prediction Gating Rules:**
The extrapolated pose $\widehat{X}_j(t)$ is adopted **if and only if** all the following conditions hold:
1. **Delay Bound:** $\tau \le \tau_{\max}^{\mathrm{pred}}$ (default: $50 \times h$, or $0.5\,\mathrm{s}$).
2. **Velocity Bound:** $\|\xi_j(t - \tau)\|_2 \le \xi_{\max}$ (default: $2.0\,\mathrm{m/s}$ linear, $1.5\,\mathrm{rad/s}$ angular).
3. **Step Bound:** $\|\tau \xi_j\| \le \Delta_{\max}^{\mathrm{extrap}}$ (default: $0.2\,\mathrm{m}$ translation, $0.2\,\mathrm{rad}$ rotation).

**Fallback Strategy:**
If any gating condition is violated:
- **Zero-Velocity Hold:** Fallback to the unextrapolated stale pose: $\widehat{X}_j(t) \leftarrow X_j(t - \tau)$.
- **Energy Safeguard:** Temporarily increase local damping $D_i$ on boundary node $i$ by factor $\kappa_{\mathrm{stale}} > 1$ (e.g., $2.0$) to dissipate residual kinetic energy and prevent oscillation.

## 5. Fault Tolerance and Dynamic Partitions

### 5.1 Packet Loss and Missing Neighbors

If communication is interrupted and no update is received for boundary node $j$ for duration $\tau > \tau_{\mathrm{timeout}}$:
1. The edge $(i, j)$ is temporarily deactivated from the active optimization set $\mathcal{E}_{\mathrm{eligible}}$.
2. Rover $\alpha$ continues local optimization over $\mathcal{E}_{\mathrm{local}}$.
3. Upon reconnection and reception of a fresh packet, $(i, j)$ is reactivated with zero initial velocity extrapolation.

### 5.2 Integration with Subgraph Partition Management (Phase 2 DSU)

The AstroMesh-X `SubgraphPartitionManager` maintains the connected components of the swarm graph via disjoint-set forests (DSU):
1. **Disconnected Swarm Components:**
   Prior to inter-rover loop closure verification, rovers operate in separate connected components. Each rover maintains its own local gauge anchor ($X_{\mathrm{anchor}} = I, \xi_{\mathrm{anchor}} \equiv 0$).
2. **Partition Merging upon Loop Closure Verification:**
   When an inter-rover candidate edge between Rover $\alpha$ and Rover $\beta$ passes geometric and Mahalanobis gating, `SubgraphPartitionManager::unify` merges the two partitions:
   - The root component retains the global gauge anchor.
   - The merged rover transitions its former local anchor into a dynamic node.
   - The distributed CORD optimizer automatically begins exchanging boundary state packets.

## 6. Simulation Architecture and Execution Modes

For upcoming implementation milestones, AstroMesh-X will support two distinct simulation execution modes:

### Mode A: Synchronous Multi-Robot Simulation (Milestone 3.5 Initial Baseline)
- **Clock:** A centralized discrete simulation coordinator advances time in lock-step increments $t_{k+1} = t_k + h$.
- **Execution:**
  1. All rovers compute local gradients $\nabla_{X_i} \mathcal{C}$ at time $t_k$.
  2. All boundary state packets are posted to simulated network queues with configurable deterministic latency $\Delta t_{\mathrm{delay}} = n \cdot h$.
  3. Rovers update local velocities and poses to $t_{k+1}$ via the semi-implicit integrator.
  4. Packets whose delivery time $\le t_{k+1}$ are delivered to recipient queues.
- **Purpose:** Deterministic regression testing, reproducibility, mathematical validation of neighbor prediction under controlled delays.

### Mode B: Asynchronous Distributed Simulation (Milestone 3.5 Extension / Milestone 3.6)
- **Clock:** Each simulated rover runs on independent thread or async loop with stochastic computation jitter.
- **Channel Model:** Simulated wireless channel with stochastic latency (log-normal distribution), packet drop probability $p_{\mathrm{loss}} \in [0.0, 0.30]$, and out-of-order delivery.
- **Purpose:** Stress-testing robustness, verifying energy dissipation under harsh communication failures, evaluating real-world communication efficiency.
